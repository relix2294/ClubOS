# Development CA и credential устройств (M0)

ТЗ §3.1 допускает на M0 локальный dev CA, если ротация описана, а приватные ключи устройств не
попадают в логи Cloud. Промышленный PKI с отзывом сертификатов запланирован на M1/M2
(DEVIATIONS D-002).

## Модель

| Субъект | Ключ | Где хранится | Сертификат |
|---------|------|--------------|------------|
| Dev CA | ECDsa P-256 | Cloud: `DevCa:Path` (`/data/dev-ca/ca.key`, права 600, отдельный Docker volume) | self-signed, 5 лет |
| Edge | ECDsa P-256, генерируется на Edge | `edge-data/edge.key` (600) | CN=edgeId, OU=edge, 90 дней |
| Устройство (Agent) | ECDsa P-256, генерируется на ПК | `%ProgramData%\ClubOS\Agent\device.key`, зашифрован DPAPI; каталог доступен только SYSTEM и Administrators | CN=deviceId, OU=device, 90 дней |

- При enrollment наружу уходит только **CSR**. Приватный ключ не покидает устройство.
- CA сам назначает subject (CN/OU). Значения из CSR игнорируются, поэтому устройство не может выбрать себе чужую идентичность.
- Enrollment-токены одноразовые, живут 24 часа. В БД хранится SHA-256 от токена.
  Токен «сжигается» атомарным `UPDATE ... WHERE used_at IS NULL`.

## Аутентификация запросов

Каждый запрос Edge→Cloud и Agent→Edge несёт заголовок `Authorization: ClubOS-Sig <JWS ES256>`:
`kid/sub` = id субъекта, `aud` = `clubos-cloud` | `clubos-edge`, время жизни 60 с, `jti`.
Сервер проверяет:
1. сертификат субъекта выпущен dev CA и не истёк;
2. CN совпадает с `kid`, OU совпадает с ролью;
3. подпись, `aud` и срок действия с допуском ±60 с на расхождение часов;
4. повтор `jti` (anti-replay кэш).

Ограничение M0 (DEVIATIONS D-007): подписывается токен, а не тело запроса. Защиту тела от
подмены на канале обеспечивает TLS. В пилоте Cloud API публикуется только за TLS (reverse proxy).
Канал Edge↔Agent в LAN на M0 идёт по HTTP.

## Ротация

**Сертификаты Edge и устройств (90 дней, `Pki:CertificateDays`)** продлеваются автоматически (M1, D-011).
- Edge за 30 дней до истечения (`Edge:CertificateRenewBeforeDays`) шлёт в Cloud CSR от своего ключа
  (`POST /api/v1/edge/renew`). Запрос подписан ещё действующим сертификатом. Проверка — раз в 6 часов.
- Агент продлевает сертификат через Edge (`POST /agent/v1/renew` → `/api/v1/edge/devices/{id}/renew`).
  Edge сразу сохраняет новый сертификат устройства.
- Ключ при продлении не меняется; ротация ключа — M2.
- Если Cloud недоступен, попытка повторяется, а 30 дней запаса покрывают долгий offline.
- Аудит: `edge.certificate_renewed`, `device.certificate_renewed`.

**Отзыв (M1, D-011).**
- «Удалить устройство» в карточке ПК (право `enrollment.manage`):
  - Cloud помечает устройство отозванным и ставит Edge команду `RevokeDevice`;
  - список отозванных дублируется в конфигурации Edge;
  - Edge удаляет сертификат устройства и отклоняет его запросы (401);
  - сессия, начатая на Edge без связи с Cloud, закрывается с расчётом.
- «Отключить Edge» на дашборде: Cloud перестаёт принимать запросы этого Edge.
- История и аудит сохраняются в обоих случаях. Вернуть ПК можно только новой регистрацией:
  `install-agent.ps1 -EnrollmentToken <новый> -ReEnroll`. Для Edge: удалить `identity.json` и `edge.key`
  и запустить с новым `CLUBOS_Edge__EnrollmentToken`.
- CRL/OCSP не нужны: Cloud и Edge сверяют сертификат с сохранённым у себя, а не только с цепочкой CA.

**Компрометация dev CA.** Остановить Cloud, удалить том `devca` (или каталог `DevCa:Path`) и
запустить Cloud: будет создан новый CA. Все Edge и устройства затем перерегистрируются по процедуре выше.
Старые сертификаты перестанут приниматься автоматически, потому что цепочка до нового CA не строится.

**Ключ подписи JWT сотрудников** (`Auth:SigningKey`). Смена ключа в env и перезапуск Cloud:
все access-токены становятся недействительны, Admin Web перелогинит пользователя через refresh.
Если `Auth:MfaEncryptionKey` не задан, секреты 2FA зашифрованы ключом, выведенным из ключа подписи:
перед сменой ключа подписи задайте отдельный `Auth:MfaEncryptionKey`, иначе всем придётся настроить 2FA заново.

## Что НЕ попадает в логи

Enrollment-токены, refresh-токены, JWT, приватные ключи и PEM не пишутся в логи и в audit. В audit
пишутся только ID токенов и субъектов. Логи Edge и Agent содержат только ID и текст ошибок.
