# Development CA и credential устройств (M0)

ТЗ §3.1 допускает на M0 локальный dev CA, если ротация описана, а приватные ключи устройств не
попадают в логи Cloud. С M2 добавлены реестр выпущенных сертификатов, список отзыва (CRL) и mTLS между ПК и
Edge (DEVIATIONS D-002, D-007); ключ CA по-прежнему хранится файлом на сервере Cloud.

## Модель

| Субъект | Ключ | Где хранится | Сертификат |
|---------|------|--------------|------------|
| Dev CA | ECDsa P-256 | Cloud: `DevCa:Path` (`/data/dev-ca/ca.key`, права 600, отдельный Docker volume) | self-signed, 5 лет |
| Edge | ECDsa P-256, генерируется на Edge | `edge-data/edge.key` (600) | CN=edgeId, OU=edge, 90 дней |
| Устройство (Agent) | ECDsa P-256, генерируется на ПК | `%ProgramData%\ClubOS\Agent\device.key`, зашифрован DPAPI; каталог доступен только SYSTEM и Administrators | CN=deviceId, OU=device, 90 дней |
| TLS Edge (API агентов) | ECDsa P-256, отдельный от ключа подписи, генерируется на Edge | `tls.key` в каталоге данных Edge (под DPAPI на Windows) | CN=edgeId, OU=edge-server, EKU serverAuth, SAN — имена и IP сервера, 90 дней |

- При enrollment наружу уходит только **CSR**. Приватный ключ не покидает устройство.
- CA сам назначает subject (CN/OU). Значения из CSR игнорируются, поэтому устройство не может выбрать себе чужую идентичность.
- Enrollment-токены одноразовые, живут 24 часа. В БД хранится SHA-256 от токена.
  Токен «сжигается» атомарным `UPDATE ... WHERE used_at IS NULL`.

## Аутентификация запросов

Каждый запрос Edge→Cloud и Agent→Edge несёт заголовок `Authorization: ClubOS-Sig <JWS ES256>`:
`kid/sub` = id субъекта, `aud` = `clubos-cloud` | `clubos-edge`, время жизни 60 с, `jti`.
Сервер проверяет:
1. сертификат субъекта выпущен dev CA и не истёк;
2. CN совпадает с `kid`, OU совпадает с ролью;
3. подпись, `aud` и срок действия с допуском ±60 с на расхождение часов;
4. повтор `jti` (anti-replay кэш);
5. **привязку к запросу (M1, D-007):** `htm` = метод, `htu` = путь с query, `bh` = base64url(SHA-256 тела).
   Подменённое тело, путь или метод дают 401, как и чужая подпись. Cloud требует привязку всегда
   (`Pki:RequireEdgeRequestBinding`), Edge — после `Edge:RequireAgentRequestBinding=true`.

**TLS Edge↔Agent (M1, D-007).** Edge после регистрации запрашивает у Cloud серверный сертификат
(`POST /api/v1/edge/server-certificate`, CSR от отдельного ключа `tls.key`) и слушает HTTPS 7443. Сертификат
продлевается за 30 дней до истечения и перевыпускается при смене IP или имён. Агент не использует системное
хранилище: он доверяет только CA, чей SHA-256 отпечаток администратор взял из Admin Web
(`GET /api/v1/pki/ca`, передаётся в `install-agent.ps1 -EdgeCaFingerprint`). Первичное получение CA —
`GET /agent/v1/ca`: агент сверяет отпечаток и проверяет, что сертификат, предъявленный в рукопожатии, выпущен этим CA.
Дальше CA хранится вместе с identity агента. Проверка цепочки строится только от этого CA (CustomRootTrust),
имя в URL должно совпадать с SAN. Канал Edge→Cloud в пилоте идёт через HTTPS (Caddy + Let's Encrypt).

**mTLS Edge↔Agent (M2, D-007).** На 7443 Edge запрашивает у клиента сертификат. Агент предъявляет сертификат
устройства со своим ключом (на Windows ключ загружается через PKCS#12 — SChannel не принимает эфемерный).
Edge проверяет его в `AgentAuth` вместе с токеном:
1. цепочка до CA устройства: CA Cloud или локальный CA бездисковых ПК; назначение clientAuth; срок действия;
2. CN совпадает с `kid` токена: сертификат другого ПК не подходит;
3. серийного номера нет в CRL.

Неверный сертификат дают 401 всегда. Отсутствие сертификата даёт 401 только при
`Edge:RequireAgentClientCertificate=true` (`install-edge.ps1 -RequireClientCertificate`): тогда закрыт и HTTP 7070.
Без сертификата всегда работают регистрация ПК, загрузка бездискового ПК и касса `/cash`.
Ключ сертификата не сверяется с ключом токена: после ротации открытое соединение ещё несёт прежний сертификат
того же ПК, а владение текущим ключом доказывает подпись. После продления агент сам открывает новый пул
соединений с новым сертификатом, прежний закрывается через минуту.

## Ротация

**Сертификаты Edge и устройств (90 дней, `Pki:CertificateDays`)** продлеваются автоматически (M1, D-011).
- Edge за 30 дней до истечения (`Edge:CertificateRenewBeforeDays`) шлёт в Cloud CSR от своего ключа
  (`POST /api/v1/edge/renew`). Запрос подписан ещё действующим сертификатом. Проверка — раз в 6 часов.
- Агент продлевает сертификат через Edge (`POST /agent/v1/renew` → `/api/v1/edge/devices/{id}/renew`).
  Edge сразу сохраняет новый сертификат устройства.
- **Ротация ключа (M2):** при каждом продлении клиент (Edge или агент) создаёт новый ключ (`edge.key.next` /
  `device.key.next`), CSR — на новый ключ, запрос подписан текущим. Ответ сохраняется в порядке «сначала ключ
  (атомарная замена файла), потом identity». Сервер (Cloud для Edge, Edge для устройств) хранит сертификат
  прежнего ключа (`PreviousCertificatePem` / `previous_certificate_pem`) и принимает его подпись, пока клиент не
  подпишет запрос новым ключом, — тогда прежний забывается. Если ответ на продление потерялся, клиент продлевает
  снова прежним ключом, и «прежний» не перезаписывается. Агенты старых версий продлевают с тем же ключом — это не
  ротация, «прежний» не заводится. Конфигурация Cloud, прочитанная до продления, не затирает новый сертификат
  устройства на Edge.
- Если Cloud недоступен, попытка повторяется, а 30 дней запаса покрывают долгий offline.
- Аудит: `edge.certificate_renewed`, `device.certificate_renewed`.

**Отзыв (M1, D-011).**
- «Удалить устройство» в карточке ПК (право `enrollment.manage`):
  - Cloud помечает устройство отозванным и ставит Edge команду `RevokeDevice`;
  - список отозванных дублируется в конфигурации Edge;
  - Edge удаляет сертификат устройства и отклоняет его запросы (401);
  - сессия, начатая на Edge без связи с Cloud, закрывается с расчётом.
- «Отключить Edge» на дашборде: Cloud перестаёт принимать запросы этого Edge.
- История и аудит сохраняются в обоих случаях. Вернуть ПК можно только новой регистрацией:
  `install-agent.ps1 -EnrollmentToken <новый> -ReEnroll`. Для Edge: удалить `identity.json` и `edge.key`
  и запустить с новым `CLUBOS_Edge__EnrollmentToken`.
- Cloud и Edge сверяют сертификат с сохранённым у себя, а не только с цепочкой CA.

**Реестр и CRL (M2, D-002).**
- Каждый выпущенный сертификат записывается в таблицу `certificates`: серийный номер, CN, роль, срок, отзыв.
  Записываются сертификаты Edge, TLS API агентов и устройств, включая продления.
- Удаление ПК или отключение Edge отзывает все действующие сертификаты субъекта (причина
  cessationOfOperation): текущий, прежний ключ и серверный TLS. Сертификаты, выпущенные до появления реестра,
  берутся из записи устройства или Edge.
- `GET /api/v1/pki/crl` отдаёт CRL в DER (`application/pkix-crl`) без входа, как принято для CRL.
  - Подписан CA; номер CRL — время выпуска в мс; nextUpdate — `Pki:CrlDays` (7 дней).
  - В списке только отозванные и ещё не истёкшие сертификаты.
  - Кэш 30 с, сбрасывается при каждом отзыве.
- Edge забирает CRL раз в `Edge:CrlRefreshSeconds` (300) и сохраняет `crl.der` в каталоге данных.
  - Перед сохранением проверяет подпись CA из своей регистрации и издателя.
  - Не заменяет список более старым (по номеру).
  - Без связи с Cloud применяет последний список, даже просроченный, и пишет предупреждение.
  - Состояние списка: `edge-cli status`, поле `crl`.
- Отозванный сертификат Edge не принимает ни в рукопожатии, ни в подписи токена, даже если конфигурация с
  удалением ПК ещё не дошла.

**Компрометация dev CA.** Остановить Cloud, удалить том `devca` (или каталог `DevCa:Path`) и
запустить Cloud: будет создан новый CA. Все Edge и устройства затем перерегистрируются по процедуре выше.
Старые сертификаты перестанут приниматься автоматически, потому что цепочка до нового CA не строится.
После смены CA у агентов нужен новый `-EdgeCaFingerprint` вместе с `-ReEnroll`.

**Ключ подписи JWT сотрудников** (`Auth:SigningKey`). Смена ключа в env и перезапуск Cloud:
все access-токены становятся недействительны, Admin Web перелогинит пользователя через refresh.
Если `Auth:MfaEncryptionKey` не задан, секреты 2FA зашифрованы ключом, выведенным из ключа подписи:
перед сменой ключа подписи задайте отдельный `Auth:MfaEncryptionKey`, иначе всем придётся настроить 2FA заново.

## Что НЕ попадает в логи

Enrollment-токены, refresh-токены, JWT, приватные ключи и PEM не пишутся в логи и в audit. В audit
пишутся только ID токенов и субъектов. Логи Edge и Agent содержат только ID и текст ошибок.
