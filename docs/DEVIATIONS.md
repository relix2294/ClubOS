# DEVIATIONS — журнал упрощений M0

Формат по ТЗ §0: **что упрощено · почему · когда должно быть исправлено**.
Каждое упрощение — сознательное и ограничено рамками M0 (ТЗ §25).

---

### D-001 · Edge local DB = SQLite WAL (не PostgreSQL)

- **Что:** Edge Controller использует SQLite в WAL-режиме, а не локальный PostgreSQL.
- **Почему:** прямо разрешено ТЗ §7.1 и §25.2.4 для раннего этапа.
- **Когда исправить:** решение SQLite vs local PostgreSQL для production Edge — отдельный ADR (ТЗ §36). Не ранее M2.

### D-002 · Development CA вместо промышленного PKI

- **Что:** индивидуальные device credential выдаёт локальный development CA; ротация описана, но упрощена.
- **Почему:** ТЗ §3.1 явно допускает локальный dev CA на M0 при условии описанной ротации и того, что приватный ключ устройства не попадает в Cloud-логи.
- **Когда исправить:** промышленный mTLS/PKI с отзывом — M1/M2 (ТЗ §27.2).

### D-003 · LockTestMode = полноэкранный overlay, без подмены Shell

- **Что:** `LockTestMode` показывает управляемый полноэкранный тестовый overlay/демо, НЕ меняет Winlogon Shell/GPO/политики.
- **Почему:** ТЗ §3.3 и §25.2.5 прямо запрещают опасную подмену системного Shell на M0.
- **Когда исправить:** настоящий Player Shell — M1 (ТЗ §26).
- **Статус (M1):** сделан Player Shell (режимы Off/Hud/Enforced): экран клуба на свободном ПК, индикатор сессии,
  итог по окончании, вход техника по PIN. Shell по-прежнему не подменяется — ограничения см. D-016.
  LockTestMode остаётся тестовой командой.

### D-004 · Минимальная аутентификация

- **Что:** реальная, но минимальная аутентификация сотрудников (не полноценный MFA/refresh-rotation из §8).
- **Почему:** §3.1 требует «минимальную реальную аутентификацию», явно запрещая фиктивную (`admin=true`). Полный AUTH-набор §8 — вне M0.
- **Когда исправить:** MFA, ротация refresh, granular permissions — M1+ (ТЗ §8).
- **Статус (M1):** сделано — ротация refresh, роли Owner/Admin/Operator с правами на backend, управление
  персоналом, временные пароли, мгновенный отзыв доступа.
  2FA (TOTP, RFC 6238) сделана:
  - обязательна для Owner/Admin на VPS (`Auth:MfaRequiredRoles`);
  - вход в два шага: challenge 5 мин, 5 попыток, защита от повтора кода;
  - секрет зашифрован AES-GCM, 10 одноразовых кодов восстановления;
  - сброс владельцем и через CLI.

  В dev-стеке 2FA добровольная, чтобы e2e и демо входили по паролю. WebAuthn/passkeys — кандидат на M2.

### D-005 · Device Simulator для 5 ПК

- **Что:** 5 «ПК» в панели — симулятор, не реальные Agent.
- **Почему:** §3.4 требует симулятор именно как отдельный, ясно маркированный инструмент; он НЕ заменяет один обязательный реальный Windows Agent.
- **Когда исправить:** не требует исправления — постоянный dev-инструмент; маркировка обязательна.

### D-006 · Boot Node / Player Shell / Remote / POS — только пустые каталоги

- **Что:** каталоги `services/boot-orchestrator`, `services/remote-broker`, `apps/player-shell` присутствуют в структуре, но не реализуются в M0.
- **Почему:** ТЗ §25.4 прямо запрещает реализацию бездиска, remote desktop, реальных платежей и «декоративных страниц» на M0.
- **Когда исправить:** по дорожной карте §26 (M3/M4).
- **Статус (M1):** Player Shell реализован внутри Windows Agent: логика в `ClubOS.Agent.Core/PlayerShell`,
  UI в `ClubOS.Agent.SessionHost` (D-016). Отдельное приложение `apps/player-shell` не нужно, пока UI
  на ПК рисует SessionHost. Каталог оставлен под будущий клиентский интерфейс (вход клиента, магазин).

### D-007 · Каналы Edge↔Agent и dev Edge↔Cloud по HTTP; подписан токен, а не тело

- **Что:** Agent→Edge (LAN) и dev Edge→Cloud идут по HTTP. Каждый запрос несёт подписанный
  ключом субъекта токен (ES256, 60 с, anti-replay), но тело запроса не подписано и не шифруется.
- **Почему:** для M0 важна индивидуальная идентичность устройств без общих секретов (§3.1).
  mTLS в LAN клуба требует выдачи серверного сертификата Edge и доверия к нему на ПК; это отдельная задача.
- **Риск:** злоумышленник в LAN клуба может читать и модифицировать трафик Edge↔Agent.
- **Когда исправить:** пилот — Cloud API только за TLS: сделано, `infrastructure/vps` (Caddy + Let's Encrypt);
  M1 — TLS или mTLS Edge↔Agent и подпись тела.

### D-008 · Near-realtime в Admin Web через polling, а не SignalR

- **Что:** Admin Web опрашивает Cloud API раз в 2–3 с (устройства, команды) и раз в 10 с (`/me`, статус Edge).
- **Почему:** ТЗ разрешает «обоснованный эквивалент». Polling проще через BFF с httpOnly-cookie и
  даёт задержку 2–3 с, чего достаточно для M0 (5–6 ПК).
- **Когда исправить:** SignalR/WebSocket push — M1, когда появятся сотни ПК и живые статусы.
- **Статус (M1):** сделан push через Server-Sent Events, а не SignalR:
  - Cloud `GET /api/v1/live` → BFF `/api/live` → EventSource в браузере;
  - сервер шлёт только подсказки «изменилось устройство/команда/сессия/аудит/Edge/персонал», данные клиент
    перечитывает через REST с обычной проверкой прав;
  - опрос остаётся страховкой раз в 30 с.

  Почему SSE: браузер не держит JWT (httpOnly-cookie за BFF), а EventSource отправляет cookie сам.
  Поток нужен только в одну сторону (действия идут через REST). SSE проходит через Caddy и BFF без отдельного
  протокола и зависимостей.

  Подсказки публикует перехватчик EF после фиксации транзакции, поэтому покрыты все пути записи. Переходы
  «не в сети» по времени публикует монитор присутствия (раз в 3 с, только пока есть подписчики). Поток живёт
  не дольше access-токена и перепроверяет сотрудника раз в 30 с.
  **Осталось:** брокер внутрипроцессный. Для нескольких экземпляров Cloud API — PostgreSQL LISTEN/NOTIFY или Redis.

### D-009 · PBKDF2-SHA256 вместо Argon2id для паролей

- **Что:** хэш паролей PBKDF2-HMAC-SHA256, 210 000 итераций (BCL, без нативных зависимостей).
- **Почему:** в .NET нет встроенного Argon2id. Для M0 PBKDF2 с OWASP-параметрами признан эквивалентом.
- **Когда исправить:** M1 — Argon2id (libsodium/Konscious) с прозрачным перехэшированием при входе.
- **Статус (M1):** закрыто — Argon2id (Konscious, m=19 MiB, t=2, p=1); хэши M0 перехэшируются при входе.

### D-010 · Cloud→Edge: HTTP long-poll вместо gRPC/WebSocket

- **Что:** Edge забирает очередь команд long-poll'ом (`GET /api/v1/edge/commands?waitSeconds=20`) и подтверждает (`ack`).
- **Почему:** это исходящее соединение, как требует §7.2. Оно проходит через любой NAT и прокси и обходится без
  дополнительной инфраструктуры. Доставка at-least-once плюс inbox на Edge дают ту же семантику.
- **Когда исправить:** по нагрузочным замерам M1–M2 (gRPC streaming при необходимости).

### D-011 · Нет отзыва сертификатов и удаления устройств

- **Что:** CRL/OCSP не реализованы. Удалить устройство или Edge из Admin Web нельзя. Автоперевыпуска сертификатов (90 дней) нет.
- **Почему:** промышленный PKI вне M0 (D-002). Процедура ротации описана в `docs/security/dev-ca.md`.
- **Когда исправить:** M1/M2 вместе с PKI.

### D-012 · UI на Tailwind без shadcn/ui

- **Что:** компоненты Admin Web (Card, Button, Badge…) написаны вручную на Tailwind CSS 4, без генератора shadcn.
- **Почему:** M0 нужно 6–7 примитивов. Это не требует CLI-генерации и лишних зависимостей, дизайн-токены лежат в `globals.css`.
- **Когда исправить:** при росте UI (M1) — миграция на shadcn/ui.

### D-013 · Одна локация и один Edge на локацию в UI; минимальный RBAC

- **Что:** Admin Web показывает первую локацию организации. Роли: Owner (всё, включая enrollment) и
  Operator (зарезервирована, UI-ограничения только для enrollment). Granular permissions нет.
- **Почему:** в пилоте M0 одна локация (Dushanbe Pilot). Tenant isolation при этом проверяется на backend для всех запросов.
- **Когда исправить:** выбор локации и полный RBAC (§8) — M1.
- **Статус (M1):** RBAC сделан (Owner/Admin/Operator, 6 прав, проверка на каждом эндпоинте).
  Сделано и остальное:
  - права по локациям: «все локации» или список, проверка на каждом эндпоинте и в live-потоке,
    чужая локация отвечает 404;
  - переключатель локаций в шапке Admin Web;
  - владелец создаёт локации, зоны и меняет тарифы (версия правила растёт, снимки идущих сессий не меняются).

  **Осталось (M2):** несколько Edge на одну локацию, расписания тарифов (день/ночь), пакеты.

### D-014 · Статусы устройств в Cloud — периодический снимок

- **Что:** Edge раз в 5 с отправляет снимок статусов (не durable). Durable-событиями идут только переходы online/offline,
  сессии и жизненный цикл команд.
- **Почему:** heartbeat каждые 10 с от каждого ПК через durable outbox раздул бы журнал без пользы.
  Потерянный снимок заменяется следующим.
- **Когда исправить:** не требует исправления. Пересмотреть при переходе на push-канал (D-010).

### D-015 · Enrollment агента требует связи Edge↔Cloud

- **Что:** Edge пересылает enrollment агента в Cloud, потому что только Cloud владеет CA. Без WAN новый ПК зарегистрировать нельзя.
  Уже зарегистрированные ПК, сессии и команды в очереди работают offline.
- **Почему:** CA и выпуск credential централизованы (§3.1). Sub-CA на Edge — это вопрос промышленного PKI.
- **Когда исправить:** M2 (промежуточный CA на Edge), если потребуется offline-enrollment.

### D-016 · Player Shell — полноэкранное приложение поверх рабочего стола, не замена Winlogon Shell

- **Что:** экран клуба — окна AgentSessionHost поверх всех (TopMost, на всех мониторах) плюс низкоуровневый хук
  клавиатуры, который глушит Win, Alt+Tab, Alt+Esc, Ctrl+Esc, Ctrl+Shift+Esc. Ctrl+Alt+Del не перехватывается.
  SessionHost закрывается через Диспетчер задач, но служба (LocalSystem) перезапускает его в сессии пользователя
  через 10–30 с (WTSQueryUserToken + CreateProcessAsUser). Explorer продолжает работать под экраном.
  Вход клиента по логину или QR на экране нет: сессию начинает администратор.
- **Почему:** ТЗ §3.3 и §25.2.5 запрещают опасную подмену системного Shell и политик без механизма отката.
  Ошибка в kiosk-режиме запирает ПК клуба. Выбранный вариант даёт рабочий «экран клуба» без этого риска.
  Вход клиента требует модуля клиентов и балансов, которого ещё нет (раздел «Будущие модули» в Admin Web).
- **Риск:** клиент, знающий Ctrl+Alt+Del → Диспетчер задач, может на несколько секунд увидеть рабочий стол
  свободного ПК. Сессия при этом не начинается и не тарифицируется.
- **Когда исправить:** M2 — Shell Launcher / Assigned Access для выделенной учётной записи игрока с процедурой
  отката. Вход клиента — вместе с модулем клиентов и балансов.

## Блокеры среды

- **ENV-1 (снят):** .NET 10 SDK установлен в облачной среде разработки; сборка и все тесты выполняются.
- **ENV-2 (снят):** Docker доступен в облачной среде. PostgreSQL 18, Testcontainers и `docker compose` проверены.
- **ENV-3 (открыт, ожидаемый):** Windows Agent на реальном Windows ПК проверяется отдельно (ТЗ §3.3),
  см. `docs/runbooks/windows-agent-install.md`. Здесь гарантируется компиляция (Linux + windows-latest CI).
